邏輯與正確性

3 項
A1 已完成

利潤只算「已繳」，新活動一開始就顯示大額虧損

高

app/api/events/route.ts:48 的總收入是 filter(a => a.paid && !a.is_free) —— 只有已經收到的錢才計入。 但場租在活動建立當下就全額計入成本。

結果是：一場 20 人、場租 2,000 的活動剛建立時，利潤顯示 −2,000，而且是紅字警示的視覺。 等收完錢才會翻正。這個數字在收款完成前一直是錯的，而收款期正是負責人最常看這頁的時候。

建議 拆成三個數字：應收（Σ 非免費者應繳）、實收（Σ 已繳）、未收（差額）。 利潤主數字用「應收」算，旁邊標註「尚有 N 人未繳，共 $X」。實收版本作為次要資訊。 這也讓催繳有了依據 —— 接上 E4 就是完整的一條線。
A2 待決策

庫存彙總 view 跨租戶全表計算

中

migrations/20260401070700_remote_schema.sql:180 的 inventory_summary 兩個 CTE 都沒有 group_id 條件： 先把所有球團的入庫與領取全表 SUM 完，才 join 回來過濾。 

restock_stats AS (
  SELECT shuttlecock_type_id, sum(quantity)
  FROM restock_records          -- ← 無 WHERE，全表
  GROUP BY shuttlecock_type_id
)

每個使用者開首頁，都在替全站所有球團算一次總和。目前資料量小感覺不到， 但成本隨全站資料成長，不是隨你自己的資料成長 —— 這是多租戶系統最典型的那種會突然痛的設計。

建議 改成 function 形式接 group_id 參數，或在 CTE 內加上 WHERE group_id = ...。 注意 view 目前是 security_invoker，RLS 會過濾結果但不會下推到 CTE 裡 —— 這正是問題所在。
A3 暫緩

結算 FIFO 全歷史重放，成本隨紀錄數線性增長

低

app/api/settlement/calculate/route.ts 每次結算都從第一筆領取開始重放，才能知道每筆消耗的是哪個批次。 這是正確的設計（CLAUDE.md 已註明不可「優化」成先過濾），但代價是每次結算都要拉全部歷史。

建議 現在不用動。等領取紀錄破千筆再考慮「批次快照」：定期把某時間點的批次剩餘量存成一列， 之後只從快照往後重放。先加個耗時 log 觀察，不要提前優化。
B

安全

3 項
B1 已裁決

球隊 PIN 只是畫面上的門，API 完全不檢查

高

PIN 驗證通過後寫入 sessionStorage，之後所有 /api/events/* 只驗證 group 層級的登入身分，不再檢查 PIN。

實際後果：同一個球團帳號登入後，任何人在瀏覽器 console 直接 fetch('/api/events?club_id=其他球隊ID') 就能讀到別隊的活動、名單與收費明細， 完全繞過 PIN。PRD 把這記為「PIN 是 UI gate」的刻意取捨，但值得重新評估： 各隊的收費資料其實沒有互相隔離。

建議 兩條路。輕的：驗證成功後發一個短效簽章 token（HttpOnly cookie 或回傳的 JWT）， /api/events/* 檢查它涵蓋的 club_id。重的：走 PRD 提到的 Phase 2， 每隊獨立帳號 + RLS 真隔離。若各隊之間本來就互相信任，那就明確寫進說明，別讓 PIN 給人錯誤的安全感。
B2 已完成

PIN 與入庫密碼可無限次嘗試

中

全專案沒有任何速率限制。 /api/clubs/[id]/verify-pin 與入庫密碼驗證都可以無限次打。 4 位數 PIN 只有 10,000 種組合，腳本幾秒就跑完。

攻擊面確實限縮在「已登入該球團帳號的人」，所以不是對外的洞。 但 PIN 的用意本來就是防同團的其他人 —— 那正是它擋不住的對象。

建議 最小成本作法：在 clubs 加 failed_attempts 與 locked_until 兩欄， 連錯 5 次鎖 15 分鐘。不需要引入 Redis 或第三方套件。
B3 已完成

/settings 沒走 middleware，靠不驗簽的 getSession 把關

低

middleware.ts:40 的 protectedPaths 只有 ['/', '/clubs']。 /settings 靠頁面自己的 getSession() 擋 —— 而 Supabase 官方明確說明 getSession() 在伺服器端只解 cookie、不驗證簽章，不應作為信任依據； getUser() 才會真的向 Auth 伺服器確認。

建議 把 /settings 加進 protectedPaths，讓它和其他頁面走同一條驗證路徑。 一行的事，而且消除了「哪些頁面用哪種驗證」的認知負擔。

效能與資料量

3 項
C1 已完成

貼一份 20 人名單，打出 21 個請求且中途失敗會靜默

高

app/(app)/clubs/[id]/page.tsx:189 建立活動後用 for...of 逐一 POST 出席者。每個請求各自做一次身分驗證加一次歸屬查詢， 20 人就是 21 個 HTTP 往返、40+ 次資料庫查詢，序列執行。 

for (const p of toAdd) {
  await fetch(`/api/events/${eventData.id}/attendees`, { ... })
  //   ↑ 沒有檢查 res.ok
}

兩個問題疊在一起：慢，而且迴圈裡完全沒檢查回應。 第 8 個人寫入失敗，畫面照樣顯示「活動建立成功」，名單就少了一個人，沒有任何提示。 這也沒有交易性 —— 失敗時已寫入的前 7 人會留在資料庫。

建議 改成單一批次端點收一個陣列，用一次 insert([...]) 寫入（Supabase 會保留陣列順序， 目前靠序列寫入維持的順序不會跑掉）。21 個請求變 2 個，順便就有了交易性與錯誤回報。
C2 待決策

每個 API 請求固定多兩次資料庫往返

中

lib/supabase/helpers.ts 的 getGroupId() 做兩件事： auth.getUser() 打 Auth 伺服器，再查一次 profiles 表。 18 個 API 路由每一個都先呼叫它，而 group_id 對同一個使用者根本不會變。

建議 把 group_id 放進 JWT 的 custom claim（Supabase Auth Hook 支援）， 從 token 直接讀，兩次往返變零。次選是用 Next.js 的 cache() 包住， 至少讓同一次請求內的多次呼叫只查一次。
C3 已完成

紀錄硬性截斷，舊資料看不到也沒說

中

領取紀錄 api/pickup/route.ts:22 固定 limit(100)， 入庫紀錄 api/inventory/history/route.ts:31 固定 limit(500)， 兩者都沒有分頁，也沒有任何「還有更多」的提示。

一個活躍球團一年輕鬆超過 100 筆領取。使用者會以為第 101 筆之前的紀錄不存在 —— 資料還在，只是看不到，這比明講「僅顯示最近 100 筆」更糟。

建議 短期：在列表底部加一行「僅顯示最近 100 筆」，一分鐘的事，先把誤導拿掉。 中期：加上以 created_at 為游標的分頁與月份篩選（跟 E2 一起做）。
D

穩定性

2 項
D1 已完成

零測試，而 FIFO 是會算錯錢的那種程式碼

高

全專案沒有任何測試檔案，也沒有測試框架。 偏偏這裡有兩段最需要測試的程式碼：FIFO 成本計算（算的是真實金額） 與 LINE 訊息解析（輸入格式不受控）。

這不是理論風險。光是這次對話就在 FIFO 相關程式碼裡發現了兩個真實的日期邊界錯誤， 兩個都是靠人工推敲才發現的 —— 那正是測試最擅長攔截的類型。

建議 不必追求覆蓋率。先裝 Vitest，只針對三件事寫測試：FIFO 批次歸屬與成本、 台北時區日界（就用這次驗證的四個臨界時間點）、LINE parser 對 PRD 列出的那幾種格式。 三個檔案就能守住最貴的那部分。
D2 已完成

出錯時使用者看到的是 Next.js 預設錯誤頁

中

全專案沒有 error.tsx、not-found.tsx 或 global-error.tsx。 任何未捕捉的例外，或使用者打錯網址進到不存在的球隊頁， 得到的都是 Next.js 的英文預設錯誤畫面 —— 跟整個介面的中文語境完全脫節， 而且沒有回首頁的路。

建議 在 app/(app)/ 放一個 error.tsx 與 not-found.tsx， 沿用側邊欄的視覺，給一句中文說明和一個「回首頁儀表板」按鈕。兩個小檔案。

功能缺口

5 項
E1 已完成

球員名冊：每場活動都要重打一次名字

中

event_attendees.display_name 是純文字，不跨活動關聯。 同一群人每週打球，名字每週重打一次；打錯字就變成另一個人。

這也讓「這個人累計來過幾次、欠多少錢」這類問題在資料上無法回答 —— 而那恰好是球隊負責人最想知道的事。

建議 加一張 club_members（club_id、姓名、預設費用、是否免費）， event_attendees 加一個 nullable 的 member_id。 建立活動時提供常用名單勾選，LINE 解析出的名字自動比對現有成員。 保留純文字欄位，臨時來的客人照樣直接打字。
E2 已完成

沒有匯出，財務資料出不去

中

全專案沒有任何 CSV 或試算表匯出。 結算試算出來的數字只能在畫面上看，要交帳、對帳、報稅或給隊員看明細，就得手動抄。

建議 三個地方各加一顆匯出鈕：結算結果、入庫紀錄、活動出席與收費明細。 純前端組 CSV 字串下載即可，不需要後端也不需要套件。注意加 BOM，否則 Excel 開中文會亂碼。
E3 已完成

紀錄一多就沒有搜尋與篩選

中

領取紀錄、活動列表都沒有搜尋框，也沒有日期或人員篩選。 唯一有篩選能力的是結算對話框。找「上個月阿明領了幾桶」只能用眼睛捲。

建議 領取紀錄加姓名搜尋與月份切換；活動列表加日期區間與「未結算 / 已結算」切換。 資料量還小，前端過濾就夠，等分頁（C3）做了再移到後端。
E4 已完成

催繳費：管道已經建好，只差沒接上

低

系統已經有完整的 LINE 推播能力（Messaging API、Flex 訊息、postback 按鈕、 每日 cron），目前只用在低庫存提醒。而未繳費名單是現成的資料。

A1 修好之後，「誰還沒繳、共多少錢」就是一個明確的數字。 在活動詳情加一顆「產生催繳訊息」，比照現有的下訂草稿做法產生可轉貼的文字 —— 複用既有元件，新增的程式碼很少，但直接解決球隊負責人每週都要做的事。

建議 先做「產生文字草稿供轉貼」，不要做自動推播 —— 催繳訊息由人決定何時發、發給誰， 自動推播容易造成困擾。這也完全不佔用 LINE 的推播額度。
E5 待決策

整個球團共用一組帳號密碼

低

一個 group 對應一組 Supabase 帳號，所有人共用。 沒有角色、沒有個人身分，created_by 欄位存的永遠是同一個人。 誰改了什麼、誰刪了哪筆紀錄，查不出來。

建議 目前規模（單一球館）這樣可用，不急。但若要開放給多球館使用， 就得走 PRD 的 Phase 2：邀請制帳號 + 角色（管理員 / 隊長 / 檢視）， 與 B1 是同一個工程。做之前先確認商業模式，別為了假想的需求提前投資。

LINE 解析器埋在頁面元件裡，測不到也用不到

中

parseLineMessage() 寫在 app/(app)/clubs/[id]/page.tsx:37 的頁面檔案裡， 是一個 50 行的純函式，卻因為位置而無法被單獨測試，也無法重用。

建議執行順序

4 梯次
第一梯

會給出錯誤答案的

利潤數字現在是錯的，而且錯在使用者最常看的時機；出席者寫入失敗完全沒有回報。 這兩件都是「系統告訴你的事情不對」，優先於一切。

A1 利潤應收／實收 · C1 批次寫入與錯誤處理

第二梯

撐住已經在跑的東西

FIFO 這次被抓到兩個日期錯誤，說明它需要測試守著。錯誤頁與紀錄截斷提示都是小工， 但直接影響使用者對系統的信任。

D1 FIFO 與 parser 測試 · F1 抽出 parser · D2 錯誤頁 · C3 截斷提示

第三梯

每週都在手動做的事

名冊、催繳、匯出、搜尋 —— 都是球隊負責人現在靠人工彌補的環節。 投入報酬率最高，而且 E4 建在既有的 LINE 模組上，幾乎沒有新基礎建設。

E1 球員名冊 · E4 催繳草稿 · E2 CSV 匯出 · E3 搜尋篩選

第四梯

成長之後才會痛的

這些現在完全感覺不到。但 B1 的隔離問題要在開放給第二個球館之前想清楚， 因為它會決定資料模型，事後改的成本高得多。

B1 球隊隔離 · B2 嘗試次數限制 · B3 middleware 一致性 · A2 view 過濾 · C2 JWT claim · A3 FIFO 快照 · E5 多帳號 · F2 檔案拆分

這份稽核怎麼做的，以及它的邊界

掃描範圍是全部 62 個 TypeScript 檔案、6 個 migration、18 個 API 路由， 以及 docs/ 下的 PRD 與效能筆記。每一項發現都附了檔名行號，你可以自己去核對。

都是讀程式碼得到的結論，沒有實際執行過。 這台 WSL 的 lightningcss 原生模組缺失，npm run build 起不來。 所以行為類的判斷（例如 A1 的利潤顯示）是從程式碼推導的，理論上可靠，但值得你在實際畫面上確認一次。 至於純視覺的介面優化建議，我刻意沒有寫 —— 沒看過實際渲染就評論視覺，那是猜測不是稽核。

優先序反映的是「錯誤的資訊比缺少的功能更傷」這個判斷。 如果你的實際痛點是每週催繳很煩，那第三梯往前提完全合理 —— 這份排序是建議，不是規定。
